## Reglas permanentes

1. **Independencia de CAWbase.** El motor es un producto separado. No copies lógica de CAWbase, no trabajes en su backend, no mantengas variantes privadas. El motor no conoce organizaciones, proyectos ni membresías.
2. **Arquitectura y ownership.** Un núcleo liviano reutilizado por Python y HTTP; el núcleo no depende de FastAPI ni de Alembic. Engine por URL (lo posee el motor) o inyectado (lo posee el host). Transacción propia o provista por el host; el motor no confirma ni revierte la transacción del host. Detalle en `docs/architecture.md` y `docs/public-api.md`.
3. **Documentación antes de implementación.** No implementes una feature sin contrato revisado; el primer prompt de cada feature solo documenta. Una vez implementada, la documentación describe el código real: «propuesto» se sustituye por «implementado» solo cuando hay código y pruebas. Los documentos permanentes conservan los contratos; la especificación de feature define alcance y aceptación y los enlaza.
4. **Preserva los cambios del usuario.** No sobrescribas, descartes ni reviertas archivos ajenos (p. ej. `docs/STAGE_3_PLAYBOOK.md`, `.DS_Store`, ambos ignorados por Git). Lee antes de editar. No uses `reset`/`clean`, no reescribas el historial (sin `--amend` ni rebase de commits existentes) y no agregues los archivos ajenos a Git. Crear commits locales **no** autoriza hacer push, publicar artefactos ni desplegar.
5. **Sin efectos al importar.** Importar no abre conexiones, no migra, no registra rutas, no carga modelos, no lee el entorno ni configura logging global. Inicialización y cierre son explícitos.
6. **API asíncrona y ambos backends.** E/S asíncrona. PostgreSQL (schema `cawbase_content_engine`) y SQLite (prefijo `cawbase_content_engine_`) se soportan y se prueban de verdad; SQLite no es una emulación de PostgreSQL. Nunca modifiques ni elimines tablas ajenas.
7. **Seguridad y aislamiento desde A01.** Todo acceso a datos de alcance exige el `scope_id` del contexto autorizado. Nunca autorices desde un identificador enviado por un frontend. API keys: solo hash, secreto mostrado una vez, sin clave universal ni endpoint de bootstrap abierto. Sin secretos, URLs de conexión ni contenido sensible en logs, errores o diagnósticos.
8. **Migraciones.** Solo el servicio HTTP independiente migra al arrancar, y **antes de escuchar** (sin HTTP durante la preparación; fallo ⇒ salida ≠ 0); la librería, el host embebido, el router montado y Lambda no migran implícitamente. Una ejecución de actualización = una transacción y un bloqueo. Solo hacia adelante; sin promesa de rollback universal.
9. **Alcance por feature.** Fuera de A01: perfiles/categorías/tipos (A02), clasificación/inferencia (A03), PDF/DOCX, protección y restauración, trabajos, OIDC/usuarios/contraseñas, elección de modelo, AWS, publicación. Fuera de A02: clasificación/inferencia y mock (A03), validación con inferencia real (A09), trabajos (A05), organizaciones/proyectos/membresías/herencia/políticas de destinos, credenciales por perfil, overrides por ejecución, purga y restauración. Consulta el documento de cada feature antes de asumir qué entra.

## Preferencias de colaboración

- Al completar trabajo solicitado sobre el repositorio, crear siempre commits locales coherentes, incluyendo la documentación pertinente y preservando cambios ajenos, salvo que el usuario indique expresamente lo contrario. Crear commits locales no autoriza hacer push, publicar artefactos ni reescribir historial.
- Cuando se solicite preparar o corregir un prompt para otro agente, entregar siempre un único prompt completo, autocontenido, actualizado y listo para copiar. Nunca entregar suplementos, parches ni instrucciones que obliguen al usuario a combinar fragmentos con un prompt anterior. Una corrección debe incorporarse al texto completo.
- Antes de crear commits, verificar la identidad Git: si solo existe la identidad inferida por el sistema (email `@<equipo>.local`), pedir nombre y email al usuario en lugar de inventarlos; si el usuario los da, configurarlos solo en este repositorio (nunca en la configuración global). Mientras tanto, continuar con el trabajo independiente.
- No volver a pedir confirmación de decisiones que el usuario ya resolvió (D-nn); aplicarlas de forma consistente.

## Mantener la documentación alineada

- Cualquier cambio de contrato se refleja en el mismo cambio en los documentos permanentes (`docs/public-api.md`, `docs/persistence-and-migrations.md`, `docs/security-and-isolation.md`, `docs/installation-and-operations.md`, `docs/architecture.md`, `docs/development.md`, y `docs/profiles-and-catalog.md` para A02) y en los de **la feature a la que pertenece** (su registro `docs/decisions/Axx-decisions.md`, la matriz de aceptación de `docs/features/Axx-…md` y, una vez implementada, su informe). Cada feature usa sus propios documentos; los de una feature cerrada solo se tocan para registrar su cierre o referencias pertinentes.
- Revisa nombres de permisos, códigos de error, estados, rutas y enlaces relativos entre documentos antes de terminar. Catálogo de permisos: **10** = 8 de A01 (`scope:read|write`, `admin:scopes:read|write`, `admin:clients:read|write`, `admin:grants:write`, `admin:diagnostics:read`) + 2 de A02 (`profiles:read|write`). **Restricción de despliegue:** no emitir claves con `profiles:*` hasta actualizar todos los runtimes que acceden a la base (un runtime A01 falla al cargar grants desconocidos y revocar no lo corrige). Enlaces sin romper **no** validan técnicamente el contrato.
- Las decisiones aprobadas (`D-nn` de A01, `D-A02-nn` de A02) solo las cambia el usuario; las propuestas (`P-nn`) se marcan como pendientes de revisión; las elecciones técnicas derivadas (`E-A02-nn`) no son decisiones de producto. No presentes una propuesta o una elección derivada como decisión.
- Comandos, rutas o nombres futuros se rotulan «propuesto / no disponible» hasta que existan y estén probados. Cada cambio de código que altere un contrato actualiza la documentación y el informe de implementación de su feature (`docs/a01-implementation-report.md`; para A02, el informe que se cree al implementarla) en el mismo cambio.
- `docs/STAGE_3_PLAYBOOK.md` es una copia de referencia; no la modifiques ni la declares actualizada. Las diferencias se registran solo en el registro de decisiones de la feature (`docs/decisions/A01-decisions.md`, `docs/decisions/A02-decisions.md`).
